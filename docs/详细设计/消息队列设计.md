# 消息队列设计文档

## 1. 概述

Prism 项目集成了统一的消息队列抽象层，支持多种消息队列后端，用于实现异步任务处理、事件驱动架构和系统解耦。

### 1.1 设计目标

- **统一接口**: 提供统一的 API，屏蔽不同队列实现的差异
- **可扩展性**: 轻松添加新的队列后端支持
- **高可用性**: 支持消息确认和重试机制
- **灵活配置**: 支持多种配置方式和队列后端切换
- **性能优化**: 针对不同场景选择合适的队列实现

### 1.2 支持的队列类型

| 队列类型 | 使用场景 | 优势 | 劣势 |
|---------|---------|------|------|
| **Memory** | 开发/测试 | 无依赖、快速 | 不持久化、单机 |
| **Redis** | 轻量级分布式 | 简单易用、功能丰富 | 性能不如专业MQ |
| **NSQ** | 中等规模分布式 | 简单部署、高可用 | 功能相对简单 |
| **Kafka** | 大规模数据流 | 高吞吐、持久化强 | 复杂度高、资源占用大 |
| **RabbitMQ** | 企业级应用 | 功能完善、可靠性高 | 性能一般 |
| **ZeroMQ** | 高性能场景 | 极高性能、低延迟 | 无持久化、无broker |

## 2. 架构设计

### 2.1 整体架构

```
┌────────────────────────────────────────────────────────┐
│                    Application Layer                    │
│  (订阅管理、节点测试、任务调度、事件通知)                 │
└─────────────────────┬──────────────────────────────────┘
                      │
                      ▼
┌────────────────────────────────────────────────────────┐
│              Queue Interface (pkg/queue)                │
│  - Publish()     发布消息                               │
│  - Subscribe()   订阅消息                               │
│  - Consume()     消费消息                               │
│  - Ack()        确认消息                                │
│  - Nack()       否定确认                                │
└─────────────────────┬──────────────────────────────────┘
                      │
        ┌─────────────┼─────────────┬──────────────┐
        ▼             ▼             ▼              ▼
   ┌────────┐    ┌────────┐    ┌────────┐    ┌──────────┐
   │ Memory │    │ Redis  │    │  NSQ   │    │  Kafka   │
   └────────┘    └────────┘    └────────┘    └──────────┘
        ▼             ▼             ▼              ▼
   ┌────────┐    ┌────────┐    ┌────────┐    ┌──────────┐
   │ 本地内存│    │ Redis  │    │ NSQ    │    │  Kafka   │
   │        │    │ Server │    │ Cluster│    │  Cluster │
   └────────┘    └────────┘    └────────┘    └──────────┘
```

### 2.2 核心接口

```go
type Queue interface {
    Publish(ctx context.Context, topic string, payload []byte) error
    PublishWithMetadata(ctx context.Context, topic string, payload []byte, metadata map[string]string) error
    Subscribe(ctx context.Context, topic string) (<-chan *Message, error)
    Consume(ctx context.Context, topic string, handler func(*Message) error) error
    Ack(ctx context.Context, msg *Message) error
    Nack(ctx context.Context, msg *Message) error
    Close() error
}
```

### 2.3 消息结构

```go
type Message struct {
    ID        string                 // 消息唯一标识
    Topic     string                 // 主题/队列名称
    Payload   []byte                 // 消息内容
    Metadata  map[string]string      // 元数据（如优先级、来源等）
    Timestamp time.Time              // 消息时间戳
    RetryCount int                   // 重试次数
}
```

## 3. 实现细节

### 3.1 Memory Queue

**实现方式**:
- 使用 Go channel 和 map 实现
- 每个 topic 对应一个 subscriber 列表
- 消息通过 channel 分发给所有订阅者

**特点**:
- ✅ 无外部依赖
- ✅ 性能最优
- ❌ 不支持持久化
- ❌ 仅支持单进程

**适用场景**:
- 开发和测试环境
- 单机应用
- 临时事件通知

### 3.2 Redis Queue

**实现方式**:
- 基于 Redis Streams
- 使用 `XADD` 发布消息
- 使用 `XREAD` 或 `XREADGROUP` 消费消息
- 使用 `XACK` 确认消息

**依赖**: `github.com/redis/go-redis/v9`

**配置示例**:
```go
queue.New("redis",
    queue.WithAddress("localhost:6379"),
    queue.WithOptions(map[string]interface{}{
        "password": "secret",
        "db":       0,
        "max_len":  10000,  // Stream 最大长度
    }),
)
```

**适用场景**:
- 轻量级分布式系统
- 已使用 Redis 的项目
- 中等消息量

### 3.3 NSQ Queue

**实现方式**:
- 使用 `Producer.Publish()` 发布消息
- 使用 `Consumer.AddHandler()` 消费消息
- 自动处理重试和失败消息

**依赖**: `github.com/nsqio/go-nsq`

**配置示例**:
```go
queue.New("nsq",
    queue.WithAddress("localhost:4150"),  // nsqd
    queue.WithOptions(map[string]interface{}{
        "lookupd": []string{"localhost:4161"},
        "channel": "prism-channel",
    }),
)
```

**适用场景**:
- 分布式微服务架构
- 需要简单部署和高可用
- 消息不需要严格顺序

### 3.4 Kafka Queue

**实现方式**:
- 使用 `SyncProducer.SendMessage()` 发布消息
- 使用 `ConsumerGroup.Consume()` 消费消息
- 支持分区和消费者组

**依赖**: `github.com/IBM/sarama`

**配置示例**:
```go
queue.New("kafka",
    queue.WithAddress("localhost:9092"),
    queue.WithOptions(map[string]interface{}{
        "group_id":     "prism-consumer-group",
        "partitions":   3,
        "replicas":     2,
        "sasl_enabled": false,
    }),
)
```

**适用场景**:
- 大规模数据流处理
- 需要消息持久化和回溯
- 高吞吐量要求

### 3.5 RabbitMQ Queue

**实现方式**:
- 使用 `Channel.Publish()` 发布消息
- 使用 `Channel.Consume()` 消费消息
- 支持 exchange、queue、binding 机制

**依赖**: `github.com/rabbitmq/amqp091-go`

**配置示例**:
```go
queue.New("rabbitmq",
    queue.WithAddress("amqp://guest:guest@localhost:5672/"),
    queue.WithOptions(map[string]interface{}{
        "exchange":      "prism-exchange",
        "exchange_type": "topic",
        "durable":       true,
    }),
)
```

**适用场景**:
- 企业级应用
- 需要复杂路由规则
- 要求消息可靠性

### 3.6 ZeroMQ Queue

**实现方式**:
- 使用 PUB-SUB 或 PUSH-PULL 模式
- 点对点通信，无 broker
- 极高性能

**依赖**: `github.com/pebbe/zmq4`

**配置示例**:
```go
queue.New("zeromq",
    queue.WithAddress("tcp://localhost:5555"),
    queue.WithOptions(map[string]interface{}{
        "socket_type": "pub-sub",  // or "push-pull"
        "bind":        true,        // bind or connect
    }),
)
```

**适用场景**:
- 高性能实时通信
- 低延迟要求
- 不需要持久化

## 4. 使用场景

### 4.1 订阅更新任务

```go
// 发布订阅更新任务
q.Publish(ctx, "subscription.update", []byte(subscriptionID))

// 消费订阅更新任务
q.Consume(ctx, "subscription.update", func(msg *queue.Message) error {
    subID := string(msg.Payload)
    return subscriptionService.Update(subID)
})
```

### 4.2 节点测试任务

```go
// 发布节点测试任务
q.PublishWithMetadata(ctx, "node.test",
    []byte(nodeID),
    map[string]string{
        "priority": "high",
        "timeout":  "30s",
    },
)

// 批量测试节点
q.Consume(ctx, "node.test", func(msg *queue.Message) error {
    nodeID := string(msg.Payload)
    return nodeService.Test(nodeID)
})
```

### 4.3 事件通知

```go
// 发布配置变更事件
q.Publish(ctx, "config.changed", []byte("routes"))

// 订阅配置变更
msgChan, _ := q.Subscribe(ctx, "config.changed")
for msg := range msgChan {
    log.Printf("Config changed: %s", string(msg.Payload))
    // 重新加载配置
    configService.Reload()
}
```

### 5.1 环境变量配置

```bash

```

## 6. 错误处理和重试

### 6.1 重试策略

```go
type RetryPolicy struct {
    MaxRetries    int           // 最大重试次数
    InitialDelay  time.Duration // 初始延迟
    MaxDelay      time.Duration // 最大延迟
    Multiplier    float64       // 延迟倍数（指数退避）
}
```

### 6.2 错误分类

- **临时错误**: 网络超时、连接失败 → 自动重试
- **永久错误**: 参数错误、业务逻辑错误 → 记录日志，不重试
- **未知错误**: 默认重试

### 6.3 死信队列

对于超过最大重试次数的消息，将其移入死信队列：

```go
if msg.RetryCount >= maxRetry {
    // 发送到死信队列
    q.Publish(ctx, "dead-letter-queue", msg.Payload)
    return ErrMaxRetriesExceeded
}
```

## 8. 最佳实践

### 8.1 选择合适的队列

- **开发/测试**: Memory
- **小型应用**: Redis
- **中型分布式**: NSQ
- **大规模/高吞吐**: Kafka
- **企业级**: RabbitMQ
- **高性能实时**: ZeroMQ

### 8.2 消息设计

- 消息尽量小，避免大对象
- 使用 JSON 或 Protobuf 序列化
- 包含必要的元数据（版本、来源等）
- 消息幂等性设计

### 8.3 性能优化

- 批量发布消息
- 合理设置并发消费者数量
- 使用连接池
- 监控和调优队列配置

### 8.4 高可用

- 使用队列集群
- 配置消息持久化
- 实现优雅关闭
- 监控队列健康状态
